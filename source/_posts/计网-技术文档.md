# 计算机网络技术文档：分层模型、HTTP、HTTPS、TCP 与网络排查


## 1. 网络分层模型

网络分层的意义是把复杂通信拆成多个职责清晰的层次。每一层只关心自己的任务，并向上层提供服务。

### 1.1 OSI 七层模型

| 层级 | 名称 | 核心职责 | 常见例子 |
| --- | --- | --- | --- |
| 7 | 应用层 | 为应用程序提供网络接口 | HTTP、FTP、SMTP、DNS |
| 6 | 表示层 | 数据格式化、加密解密、压缩解压 | TLS、编码转换 |
| 5 | 会话层 | 建立、维护、管理会话 | 会话管理 |
| 4 | 传输层 | 端到端传输、可靠性、流控 | TCP、UDP |
| 3 | 网络层 | IP 寻址、路由选择 | IP、ICMP |
| 2 | 数据链路层 | MAC 寻址、帧传输、差错检测 | Ethernet、ARP |
| 1 | 物理层 | 比特流传输 | 网线、光纤、无线电 |

### 1.2 TCP/IP 四层模型

实际工程中更常使用 TCP/IP 四层模型：

| TCP/IP 层 | 对应 OSI | 常见协议 |
| --- | --- | --- |
| 应用层 | 应用层、表示层、会话层 | HTTP、DNS、FTP、SMTP |
| 传输层 | 传输层 | TCP、UDP |
| 网络层 | 网络层 | IP、ICMP |
| 网络接口层 | 数据链路层、物理层 | Ethernet、ARP、Wi-Fi |

数据发送时从应用层一路向下封装，接收时从网络接口层一路向上解封装。

```text
应用数据 -> TCP/UDP 段 -> IP 包 -> 以太网帧 -> 比特流
```

## 2. 从输入 URL 到网页显示

在浏览器地址栏输入 URL 到页面展示，典型过程如下：

1. 浏览器解析 URL，确认协议、域名、端口、路径和参数。
2. 查询浏览器缓存、系统缓存和 hosts 文件。
3. 通过 DNS 把域名解析为 IP 地址。
4. 根据目标 IP 和端口建立连接，HTTP/1.1、HTTP/2 通常基于 TCP，HTTPS 还需要 TLS 握手。
5. 浏览器发送 HTTP 请求。
6. 服务器接收请求，经过网关、应用服务、数据库或缓存等处理，生成 HTTP 响应。
7. 浏览器接收响应，解析 HTML、CSS、JavaScript 和图片等资源。
8. 构建 DOM、CSSOM、渲染树，进行布局、绘制和合成。
9. 连接可能复用，也可能通过 TCP 四次挥手关闭。

过程中可能涉及的协议：

| 阶段 | 协议 |
| --- | --- |
| 域名解析 | DNS |
| 局域网寻址 | ARP |
| 路由转发 | IP |
| 可靠传输 | TCP |
| 安全传输 | TLS |
| 应用语义 | HTTP |

## 3. DNS 解析

DNS 用于把域名解析成 IP 地址。

### 3.1 解析流程

常见递归解析过程：

1. 浏览器先查自己的 DNS 缓存。
2. 操作系统查询本地缓存和 hosts 文件。
3. 请求本地 DNS 服务器。
4. 如果本地 DNS 没有缓存，向根域名服务器查询。
5. 根域名服务器返回顶级域名服务器地址，例如 `.com`、`.cn`。
6. 本地 DNS 向顶级域名服务器查询。
7. 顶级域名服务器返回权威域名服务器地址。
8. 本地 DNS 向权威域名服务器查询。
9. 权威域名服务器返回目标域名的 IP 地址。
10. 本地 DNS 缓存结果并返回给客户端。

### 3.2 递归查询与迭代查询

| 类型 | 含义 |
| --- | --- |
| 递归查询 | 客户端只问一次，DNS 服务器负责查到底并返回最终结果 |
| 迭代查询 | DNS 服务器返回下一步该问谁，查询方继续向下查询 |

客户端到本地 DNS 通常是递归查询，本地 DNS 到根、顶级、权威 DNS 通常是迭代查询。

### 3.3 DNS 缓存与 TTL

DNS 记录通常带有 TTL，用于控制缓存时间。

优点：

- 减少 DNS 查询延迟。
- 降低权威 DNS 压力。

缺点：

- 域名切换 IP 后，旧缓存可能继续生效一段时间。

线上变更域名解析前，常先降低 TTL，等缓存逐步过期后再切换。

## 4. HTTP 基础

HTTP 是应用层协议，定义客户端和服务端之间的请求响应语义。

### 4.1 HTTP 请求

HTTP 请求通常包括：

```text
请求行
请求头
空行
请求体
```

示例：

```http
GET /index.html HTTP/1.1
Host: example.com
User-Agent: curl/8.0
Accept: */*
```

常见方法：

| 方法 | 含义 |
| --- | --- |
| GET | 获取资源 |
| POST | 提交数据或创建资源 |
| PUT | 整体更新资源 |
| PATCH | 部分更新资源 |
| DELETE | 删除资源 |
| HEAD | 只获取响应头 |
| OPTIONS | 查询支持的方法或跨域预检 |

### 4.2 HTTP 响应

HTTP 响应通常包括：

```text
状态行
响应头
空行
响应体
```

示例：

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 1024
```

### 4.3 常见状态码

| 分类 | 含义 | 常见状态码 |
| --- | --- | --- |
| 1xx | 请求已接收，需要继续处理 | 100 Continue |
| 2xx | 请求成功 | 200 OK、201 Created、204 No Content |
| 3xx | 重定向 | 301、302、304、307、308 |
| 4xx | 客户端错误 | 400、401、403、404、409、429 |
| 5xx | 服务端错误 | 500、502、503、504 |

常见状态码说明：

- `200 OK`：请求成功。
- `301 Moved Permanently`：永久重定向。
- `302 Found`：临时重定向。
- `304 Not Modified`：资源未修改，可使用缓存。
- `400 Bad Request`：请求格式错误。
- `401 Unauthorized`：未认证。
- `403 Forbidden`：已认证但无权限。
- `404 Not Found`：资源不存在。
- `429 Too Many Requests`：请求过多，被限流。
- `500 Internal Server Error`：服务端内部错误。
- `502 Bad Gateway`：网关从上游收到无效响应。
- `503 Service Unavailable`：服务不可用。
- `504 Gateway Timeout`：网关等待上游超时。

## 5. HTTP 版本演进

### 5.1 HTTP/1.0

特点：

- 默认非持久连接。
- 每个请求通常建立一次 TCP 连接。
- 无状态，请求之间没有天然关联。

缺点：

- 频繁建连和断连成本高。
- TCP 慢启动重复发生。

### 5.2 HTTP/1.1

特点：

- 默认持久连接。
- 支持管线化，但实际使用较少。
- 支持 Host 头，可以同一 IP 承载多个域名。
- 支持分块传输、缓存控制等机制。

HTTP/1.1 的主要问题是队头阻塞。虽然连接可复用，但同一连接上的响应仍然要按顺序返回，前一个请求慢会阻塞后续响应。

### 5.3 HTTP/2

特点：

- 二进制协议。
- 多路复用。
- 头部压缩 HPACK。
- 服务器推送。
- 一个 TCP 连接上可以并发多个 stream。

HTTP/2 解决了 HTTP 层面的队头阻塞，但仍然受 TCP 队头阻塞影响。如果 TCP 丢包，整个连接上的多个 stream 都可能受影响。

### 5.4 HTTP/3

HTTP/3 基于 QUIC，QUIC 基于 UDP。

特点：

- 多路复用，且每个流相对独立。
- 减少 TCP 队头阻塞影响。
- 内置 TLS 1.3。
- 支持连接迁移，例如移动网络切换。

HTTP/3 常用于对延迟敏感、弱网环境、移动端体验要求较高的场景。

## 6. HTTPS 与 TLS

HTTPS 可以理解为：

```text
HTTPS = HTTP + TLS
```

它解决三类问题：

| 能力 | 说明 |
| --- | --- |
| 机密性 | 传输内容加密，防止被窃听 |
| 完整性 | 防止内容被篡改 |
| 身份认证 | 通过证书确认服务端身份 |

### 6.1 HTTP 与 HTTPS 区别

| 维度 | HTTP | HTTPS |
| --- | --- | --- |
| 安全性 | 明文传输 | 加密传输 |
| 默认端口 | 80 | 443 |
| 证书 | 不需要 | 需要 CA 证书 |
| 性能 | 少一次 TLS 握手 | 现代 TLS 成本已大幅降低 |
| 防篡改 | 弱 | 强 |

### 6.2 对称加密与非对称加密

| 类型 | 特点 | 用途 |
| --- | --- | --- |
| 对称加密 | 加解密使用同一个密钥，速度快 | 加密实际传输数据 |
| 非对称加密 | 公钥加密、私钥解密，速度较慢 | 身份认证、密钥交换 |

TLS 通常不是全程使用非对称加密。实际过程是先用非对称加密或密钥交换算法协商会话密钥，再用对称加密传输数据。

### 6.3 TLS 握手简化流程

以 TLS 1.2 的直观理解为例：

1. 客户端发送支持的协议版本、随机数、加密套件列表。
2. 服务端返回选择的加密套件、随机数和证书。
3. 客户端验证证书是否合法。
4. 双方协商或生成会话密钥。
5. 后续数据使用会话密钥进行对称加密传输。

TLS 1.3 简化了握手流程，减少了往返次数，安全性也更好。

## 7. Cookie 与 Session

### 7.1 Cookie

Cookie 保存在客户端。服务端通过响应头让浏览器保存 Cookie，浏览器后续访问同一站点时会携带 Cookie。

典型响应头：

```http
Set-Cookie: sid=abc123; Path=/; HttpOnly; Secure; SameSite=Lax
```

典型请求头：

```http
Cookie: sid=abc123
```

常见属性：

| 属性 | 作用 |
| --- | --- |
| HttpOnly | 禁止 JavaScript 读取，降低 XSS 窃取风险 |
| Secure | 只在 HTTPS 下发送 |
| SameSite | 降低 CSRF 风险 |
| Expires/Max-Age | 控制过期时间 |
| Domain/Path | 控制发送范围 |

### 7.2 Session

Session 保存在服务端。客户端通常只保存一个 Session ID，服务端通过这个 ID 找到用户状态。

优点：

- 状态数据不直接暴露给客户端。
- 便于服务端统一管理登录状态。

缺点：

- 服务端需要存储状态。
- 分布式系统需要考虑 Session 共享，例如 Redis、粘性会话或无状态 Token。

### 7.3 Cookie 与 Session 对比

| 维度 | Cookie | Session |
| --- | --- | --- |
| 存储位置 | 客户端 | 服务端 |
| 安全性 | 客户端可见，需保护 | 相对更安全 |
| 容量 | 较小 | 取决于服务端 |
| 分布式扩展 | 简单 | 需要共享存储或路由策略 |

## 8. TCP 基础

TCP 是面向连接、可靠、基于字节流的传输层协议。

核心特征：

- 面向连接。
- 可靠传输。
- 按序到达。
- 字节流协议。
- 一对一通信。
- 支持流量控制和拥塞控制。

TCP 常用于 HTTP、HTTPS、FTP、SMTP 等需要可靠传输的协议。

## 9. TCP 三次握手

三次握手用于建立 TCP 连接，并同步双方的初始序列号。

流程：

```text
客户端 -> 服务端：SYN，seq = x
服务端 -> 客户端：SYN + ACK，seq = y，ack = x + 1
客户端 -> 服务端：ACK，seq = x + 1，ack = y + 1
```

连接建立后，双方进入 `ESTABLISHED` 状态。

### 9.1 为什么不能是两次握手

两次握手的问题：

- 无法确认客户端收到了服务端的初始序列号。
- 服务端无法判断客户端是否具备接收能力。
- 历史 SYN 报文可能导致服务端误建立连接。
- 如果客户端的 SYN 因网络阻塞后重复到达，服务端可能为旧请求分配资源，造成浪费。

三次握手的第三次 ACK 是客户端对服务端初始序列号的确认，也是服务端确认“客户端确实能收到服务端数据”的依据。

### 9.2 为什么不是四次握手

三次握手已经完成了双方发送能力、接收能力和初始序列号同步。再增加一次握手不能带来必要的新信息，只会增加连接建立延迟。

### 9.3 第一次握手丢失

客户端发送 SYN 后收不到 SYN+ACK，会触发 SYN 超时重传。重传达到上限后连接建立失败。

### 9.4 第二次握手丢失

客户端没有收到 SYN+ACK，会重传第一次握手的 SYN；服务端没有收到第三次 ACK，也会重传第二次握手的 SYN+ACK。

### 9.5 第三次握手丢失

服务端没有收到客户端 ACK，会重传 SYN+ACK。客户端收到重复 SYN+ACK 后再次发送 ACK。

## 10. TCP 四次挥手

TCP 是全双工协议，两个方向的数据流需要分别关闭，因此通常需要四次挥手。

流程：

```text
主动关闭方 -> 被动关闭方：FIN
被动关闭方 -> 主动关闭方：ACK
被动关闭方 -> 主动关闭方：FIN
主动关闭方 -> 被动关闭方：ACK
```

典型状态变化：

```text
主动关闭方：ESTABLISHED -> FIN_WAIT_1 -> FIN_WAIT_2 -> TIME_WAIT -> CLOSED
被动关闭方：ESTABLISHED -> CLOSE_WAIT -> LAST_ACK -> CLOSED
```

### 10.1 CLOSE_WAIT 的意义

被动关闭方收到 FIN 后，会先回复 ACK，表示“我知道你要关闭了”。但被动关闭方可能还有数据要发送，或者还有业务逻辑和资源需要处理，因此进入 `CLOSE_WAIT`。

如果服务端出现大量 `CLOSE_WAIT`，通常说明应用层没有正确关闭连接，例如没有调用 `close()`。

### 10.2 TIME_WAIT 的意义

主动关闭方最后会进入 `TIME_WAIT`，等待 2MSL。

意义：

- 确保最后一个 ACK 能到达服务端。如果 ACK 丢失，服务端会重传 FIN，客户端仍能再次回复 ACK。
- 等待旧连接的数据包在网络中自然消失，避免影响未来相同四元组的新连接。

四元组是：

```text
源 IP、源端口、目标 IP、目标端口
```

### 10.3 为什么 TIME_WAIT 是 2MSL

MSL 是 Maximum Segment Lifetime，表示报文在网络中的最大生存时间。

等待 2MSL 可以覆盖：

- 最后一个 ACK 到达服务端的最长时间。
- 服务端因没收到 ACK 而重传 FIN 到达客户端的最长时间。

也可以理解为给旧报文足够时间从网络中消失。

### 10.4 四次挥手能变成三次吗

可以。在被动关闭方没有数据要发送，并且开启 TCP 延迟确认时，第二次 ACK 和第三次 FIN 可能合并发送，看起来像三次挥手。

### 10.5 挥手丢包场景

第一次挥手丢失：

```text
主动关闭方重传 FIN。
```

第二次挥手丢失：

```text
主动关闭方收不到 ACK，会重传 FIN。
```

第三次挥手丢失：

```text
被动关闭方重传 FIN。
主动关闭方如果处于 FIN_WAIT_2 且超时，可能直接关闭连接。
```

第四次挥手丢失：

```text
被动关闭方重传 FIN。
主动关闭方重传 ACK，并重置 2MSL 定时器。
```

## 11. TCP 为什么可靠

TCP 可靠性由多个机制共同保证：

| 机制 | 作用 |
| --- | --- |
| 三次握手 | 建立可靠连接，协商初始序列号 |
| 序列号 | 标识字节流位置，支持排序和去重 |
| 确认应答 ACK | 告诉发送方哪些数据已收到 |
| 校验和 | 检测数据传输错误 |
| 超时重传 | ACK 超时未收到时重发 |
| 快速重传 | 收到多个重复 ACK 时提前重发 |
| 流量控制 | 防止接收方缓冲区被打爆 |
| 拥塞控制 | 防止网络过载 |
| 四次挥手 | 可靠关闭连接 |

TCP 发送窗口：

```text
swnd = min(cwnd, rwnd)
```

其中：

- `cwnd` 是拥塞窗口，由网络拥塞状态决定。
- `rwnd` 是接收窗口，由接收方缓冲区能力决定。
- 发送方实际发送窗口取二者较小值。

## 12. 流量控制

流量控制解决的是“发送方不要把接收方压垮”。

接收方会通过 TCP 头部中的窗口字段告诉发送方自己还能接收多少数据。发送方根据接收窗口调整发送速度。

如果接收窗口为 0，发送方会暂停发送，并通过窗口探测机制定期确认窗口是否恢复。

## 13. 拥塞控制

拥塞控制解决的是“发送方不要把网络压垮”。

### 13.1 慢启动

连接刚建立时，拥塞窗口 `cwnd` 较小，然后指数增长。

```text
每经过一个 RTT，cwnd 大约翻倍。
```

当 `cwnd` 超过慢启动阈值 `ssthresh` 后，进入拥塞避免。

### 13.2 拥塞避免

拥塞避免阶段增长变慢：

```text
每经过一个 RTT，cwnd = cwnd + 1
```

### 13.3 超时重传

如果发生 RTO 超时，说明网络可能已经比较拥塞。典型处理：

```text
ssthresh = cwnd / 2
cwnd = 1
进入慢启动
```

### 13.4 快速重传与快速恢复

当发送方收到 3 个连续重复 ACK 时，通常认为某个报文段丢失，但网络不一定完全拥塞。

典型处理：

```text
ssthresh = cwnd / 2
cwnd = ssthresh + 3
重传丢失的数据段
后续每收到重复 ACK，cwnd = cwnd + 1
收到新的 ACK 后，cwnd = ssthresh，进入拥塞避免
```

## 14. TCP 粘包与拆包

TCP 是字节流协议，不保留应用层消息边界。

因此可能出现：

- 应用层一个完整消息被 TCP 拆成多个包发送。
- 多个小消息被 TCP 合并到同一次接收中。

这就是常说的粘包和拆包。

解决方式：

| 方案 | 说明 |
| --- | --- |
| 固定长度 | 每个消息长度固定，不足补齐 |
| 分隔符 | 用 `\n` 等特殊字符作为消息边界 |
| 长度字段 | 消息头中携带 body 长度，最常用 |
| TLV | Type-Length-Value，扩展性好 |

示例：

```text
| magic | version | length | body |
```

HTTP 通过 `Content-Length` 或 `Transfer-Encoding: chunked` 解决消息边界问题。

## 15. TCP 与 UDP

### 15.1 对比

| 维度 | TCP | UDP |
| --- | --- | --- |
| 是否连接 | 面向连接 | 无连接 |
| 可靠性 | 可靠 | 不保证可靠 |
| 顺序 | 保证按序到达 | 不保证顺序 |
| 传输形式 | 字节流 | 数据报 |
| 通信方式 | 一对一 | 一对一、一对多、多播、广播 |
| 首部大小 | 通常 20 字节起 | 8 字节 |
| 速度 | 相对慢 | 相对快 |
| 典型应用 | HTTP、FTP、SMTP | DNS、语音视频、游戏、QUIC |

### 15.2 如何选择

优先 TCP：

- 需要可靠传输。
- 数据不能丢。
- 顺序非常重要。
- 实现复杂度希望低。

优先 UDP：

- 对实时性要求高。
- 可以容忍少量丢包。
- 希望自定义可靠性策略。
- 需要多播或广播。

QUIC 选择基于 UDP，不是不需要可靠性，而是把可靠性、拥塞控制、加密和多路复用放到了用户态协议中实现。

## 16. IP、MAC、ARP 与 ICMP

### 16.1 IP 地址与 MAC 地址

| 地址 | 所属层级 | 作用 |
| --- | --- | --- |
| IP 地址 | 网络层 | 标识网络中的主机和路由位置 |
| MAC 地址 | 数据链路层 | 标识局域网内的网卡设备 |

IP 地址是逻辑地址，会随网络位置变化。MAC 地址是网卡硬件地址，通常固定。

### 16.2 ARP

ARP 用于根据目标 IP 查询局域网内目标设备的 MAC 地址。

流程：

```text
主机广播：谁拥有这个 IP？
目标主机回复：这个 IP 对应我的 MAC。
```

如果目标 IP 不在同一网段，主机会通过 ARP 查询网关的 MAC 地址，把数据先发给网关。

### 16.3 ICMP

ICMP 用于传输网络控制和错误报告信息。

常见用途：

- 目标不可达。
- TTL 超时。
- 回显请求和回显响应。

### 16.4 Ping

Ping 基于 ICMP Echo Request 和 ICMP Echo Reply。

流程：

1. 发起方解析域名得到 IP。
2. 向目标 IP 发送 ICMP Echo Request。
3. 目标收到后返回 ICMP Echo Reply。
4. 发起方计算 RTT，并统计丢包率。

Ping 不通不一定代表服务不可用，可能是目标禁用了 ICMP，或防火墙丢弃了 ICMP 包。

## 17. SYN 攻击与防护

SYN Flood 是典型的 TCP 半连接攻击。

攻击方式：

```text
攻击者大量发送 SYN，但不完成第三次握手。
服务端维护大量 SYN_RECV 半连接，占用队列和资源。
```

防护方式：

- 开启 SYN Cookie。
- 使用 SYN Proxy 防火墙。
- 增大半连接队列。
- 缩短 SYN_RECV 超时时间。
- 限流异常来源 IP。
- 使用负载均衡或高防服务分摊流量。

常见参数示例：

```bash
net.ipv4.tcp_syncookies = 1
net.ipv4.tcp_max_syn_backlog = 4096
```

参数需要结合系统版本、业务流量和压测结果谨慎调整。

## 18. TIME_WAIT 过多

### 18.1 危害

如果客户端有大量 `TIME_WAIT`：

- 可能占满本地临时端口。
- 短时间无法向同一目标四元组建立新连接。

如果服务端有大量 `TIME_WAIT`：

- 占用内存。
- 占用连接管理结构。
- 增加内核维护成本。

不过 `TIME_WAIT` 本身是 TCP 正常状态，不应一看到就认为是故障。要结合数量、增长速度、端口耗尽情况和连接模式判断。

### 18.2 优化方向

优先从架构和连接复用优化：

- 使用 HTTP Keep-Alive。
- 使用连接池。
- 减少短连接。
- 调整客户端并发和超时。
- 让更合适的一方主动关闭连接。

Linux 参数方向：

```bash
net.ipv4.tcp_tw_reuse = 1
net.ipv4.tcp_timestamps = 1
net.ipv4.tcp_max_tw_buckets = 18000
```

说明：

- `tcp_tw_reuse` 允许客户端在一定条件下复用处于 TIME_WAIT 的连接。
- `tcp_timestamps` 是复用判断的重要条件之一。
- `tcp_max_tw_buckets` 超过阈值后，内核可能直接清理 TIME_WAIT 连接。

不要为了减少 TIME_WAIT 盲目调小内核参数，否则可能引入旧包串扰、连接异常等问题。

## 19. 常见网络问题排查

### 19.1 域名解析问题

```bash
nslookup example.com
dig example.com
dig +trace example.com
```

关注：

- 解析出的 IP 是否正确。
- 是否命中旧缓存。
- TTL 是否符合预期。
- 权威 DNS 是否正常。

### 19.2 连通性问题

```bash
ping <host>
traceroute <host>
tracepath <host>
```

Windows 可用：

```powershell
Test-NetConnection <host> -Port 443
tracert <host>
```

关注：

- 是否能到达目标。
- 丢包发生在哪一跳。
- RTT 是否异常升高。

### 19.3 端口监听与连接状态

```bash
ss -lntp
ss -antp
netstat -antp
```

常见状态：

| 状态 | 含义 |
| --- | --- |
| LISTEN | 服务端监听 |
| SYN_SENT | 客户端已发送 SYN |
| SYN_RECV | 服务端收到 SYN，等待第三次握手 |
| ESTABLISHED | 连接已建立 |
| FIN_WAIT_1 | 主动关闭方发送 FIN |
| FIN_WAIT_2 | 主动关闭方收到 ACK，等待对方 FIN |
| CLOSE_WAIT | 被动关闭方收到 FIN，等待应用关闭 |
| LAST_ACK | 被动关闭方发送 FIN，等待 ACK |
| TIME_WAIT | 主动关闭方等待 2MSL |

### 19.4 HTTP 问题

```bash
curl -v http://example.com
curl -I https://example.com
curl --resolve example.com:443:1.2.3.4 https://example.com
```

关注：

- DNS 解析。
- TCP 是否连接成功。
- TLS 握手是否成功。
- HTTP 状态码。
- 响应头。
- 总耗时和各阶段耗时。

### 19.5 抓包

```bash
tcpdump -i eth0 host 1.2.3.4 -nn
tcpdump -i eth0 port 443 -w out.pcap
```

Wireshark 可以打开 `.pcap` 文件做图形化分析。

常看内容：

- SYN、SYN+ACK、ACK 是否完整。
- 是否有重传。
- 是否有 RST。
- RTT 是否异常。
- TLS 握手失败原因。

## 20. 面试速记

### 20.1 OSI 七层

```text
应用层、表示层、会话层、传输层、网络层、数据链路层、物理层。
```

### 20.2 TCP/IP 四层

```text
应用层、传输层、网络层、网络接口层。
```

### 20.3 TCP 三次握手

```text
SYN -> SYN+ACK -> ACK
```

作用：

- 同步双方初始序列号。
- 确认双方发送和接收能力。
- 避免历史连接干扰。

### 20.4 TCP 四次挥手

```text
FIN -> ACK -> FIN -> ACK
```

原因：

- TCP 是全双工，两个方向需要分别关闭。
- 被动关闭方收到 FIN 后，可能还有数据要发送。

### 20.5 TCP 可靠性

```text
序列号、确认应答、校验和、超时重传、快速重传、流量控制、拥塞控制。
```

### 20.6 TIME_WAIT

```text
确保最后 ACK 可重传。
等待旧连接数据包消失。
持续时间通常是 2MSL。
```

### 20.7 HTTP 与 HTTPS

```text
HTTPS = HTTP + TLS
```

HTTPS 提供加密、防篡改和身份认证。

### 20.8 Cookie 与 Session

```text
Cookie 存客户端。
Session 存服务端。
客户端通常通过 Cookie 携带 Session ID。
```

### 20.9 TCP 与 UDP

```text
TCP 面向连接、可靠、字节流、保证顺序。
UDP 无连接、不保证可靠、数据报、不保证顺序。
```

### 20.10 粘包拆包

```text
TCP 是字节流，没有应用层消息边界。
解决方式是固定长度、分隔符、长度字段或 TLV。
```

## 21. 总结

计算机网络可以围绕三条主线学习：

1. 分层：不同协议在哪一层，解决什么问题。
2. 一次请求：DNS、TCP、TLS、HTTP 如何串起来。
3. 可靠传输：TCP 如何建连、传输、控速、断连和处理异常。

工程排查时不要只背概念，要把现象映射到层次：

- 域名问题看 DNS。
- 建连问题看 TCP 握手。
- 证书问题看 TLS。
- 状态码问题看 HTTP。
- 慢请求问题拆 DNS、连接、TLS、服务端处理和下载耗时。
- 连接堆积问题看 `SYN_RECV`、`ESTABLISHED`、`CLOSE_WAIT`、`TIME_WAIT` 等状态。

把网络问题按层拆开，定位路径会清楚很多。
